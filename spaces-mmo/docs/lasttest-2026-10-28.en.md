# Load test 2026-10-28: 100 figures, 10 minutes, big and nano

Measured with `tests/perf/live-load.ts` against the running production ([betrieb.en.md](betrieb.en.md), "Lasttest gegen die
laufende Welt"). 100 guest figures played through the web process on big (loopback port 3900): picking up driftwood and
shells, putting wood on the fire, selling shells to Kalle, market, inventory, "wer", going through the exits, with a
pause of 1 to 3 s between two commands. Each command was measured from sending to the first answer for the figure;
after 10 s it counts as unanswered. Alongside, every 15 s: CPU and memory of each container (`docker stats`), memory of
the machines, size of `world.sqlite` and WAL on nano, metrics of the world Space (dashboard on big).

## Result

| | Idle (3 figures, 60 s, afterwards) | Load (100 figures, 600 s) |
|---|---|---|
| Commands | 79 | 7,704 (12.8/s) |
| Response median | 204 ms | 4,280 ms |
| Response p95 | 356 ms | 9,116 ms |
| unanswered after 10 s | 1 of 79 (1 %) | 1,939 (25 %) |
| rejected (game rule: no path, too far, too late) | 9 | 1,883 (24 %) |
| CPU Space process (nano) | ≈ 15 % | avg 108 %, max 123 % |
| Commits in the world Space | ≈ 1,100/min | avg 7,700/min |

The 1 % unanswered at idle are commands to which the game sends nothing (for example a step onto the figure's own
position); under load the share is real waiting.

**The bottleneck is the Space process on nano.** It ran at a little over one core for the whole 10 minutes (the main
thread and the writer thread of the SQLite store); all other processes stayed almost idle: world worker on nano avg
6 %, on big ≈ 0 %, web avg 3 %, NPCs avg 4 %. The workers wait for the Space, not the other way round. More world
workers therefore do not help; it only gets faster if each command costs the Space less (fewer commits and claims per
command) or if the Space uses more cores.

## What the Space process computes for

CPU profile of the Space process (`node --cpu-prof`) on the development machine, the same test with 50 figures, 60 s,
SQLite and all NPCs (median 40 ms, p95 102 ms; the process was busy about a third of the time). Self time without idle:

| Area | Share |
|---|---|
| Store (draft, SQLite, parts: `draft.ts`, `sqlite.ts`, `parts.ts`) | 23 % |
| Node and runtime | 22 % |
| Scanning entries (`core.list`, `find`, `probe`, `matches`, `expire`) | 20 % |
| remaining core logic (commit, settle, write) | 13 % |
| copying, measuring, encoding JSON | 9 % |
| Service and socket | 6 % |
| Garbage collection | 4 % |
| Request claims | 2 % |

Under load every player command came with about 9 additional commits (7,739 instead of 1,132 commits per minute at 770
commands per minute).

## Proposals

1. **Space onto the stronger machine (operations, immediately).** Locally, the same test with half as many figures
   answered with a median of 40 ms instead of 4.3 s. The Space process needs one fast core; nano is a small VM. Space
   and world worker on big, nano as the second world worker: no code, only moving file and tunnels.
2. **An index of entries by type (core).** `list`, `find`, `probe` and `expire` today walk all entries; a list per type
   (and per key field such as `charId`, `location`, `room`) makes a read as expensive as its hits.
3. **One command, one commit (core and world).** Around a dozen calls per command, each with its own commit; a call that
   carries several steps in one transaction saves commits, claims, rounds and file growth.
4. **Outputs not as entries (world).** Every command writes at least one `Msg` with a lease (up to 1,695 at once).
   Answers to a figure can go through the result of the command or the mailbox (`notify`, `events`).
5. **Less work per commit in the store (core).** Bundle waiting commits into one write, measure sizes only for changed
   entries.
6. **Split the world (architecture).** A Space is one process and one core; island groups as separate Spaces spread the
   load over several cores and machines.
7. **Keep the file small (operations).** `VACUUM` in a quiet minute or `auto_vacuum=incremental`; this does not make the
   game faster.

Charts: the dashboard "Lasttest spaces-mmo" (claude.ai, private).

### Who keeps the Space busy (local, 200 figures, 60 s)

Counted in the Space service per connection and call (`tests/perf/space-cost.ts` with `LOAD_BOTS=200`, development machine):

| Call | per second |
|---|---|
| all | 1,818 |
| `readAll` of the command worker | 1,270 (Exit 259, Character 160, Room 140, Spot 132, Item 117, Session 105, Account 79, Fog 72, Offer 70, Intent 69, Beacon 38 …) |
| `batch` (begin and commit of a command) | 187 |
| `write`, `take` | 244 |
| `changes` (web) | 71 |

Around 13 reads per command, each its own call, and all on the one core of the Space process. Hence the **mirror** in the
command worker (`Mirror` in `server/space.ts`): it reads the world once, follows the change stream and answers the
reads of a command without a transaction itself; per command it asks the Space only for its revision and waits until it
has reached it (so it sees at least what was committed before the command). Takes, writes and everything under a
transaction still go to the Space. `SPACES_MMO_MIRROR=0` switches it off.

| local, 200 figures, 60 s | without mirror | with mirror |
|---|---|---|
| Calls to the Space per second | 1,818 | 1,043 |
| Commands per second | 54.5 | 67.9 |
| Response median / p95 | 606 / 1,581 ms | 75 / 353 ms |
| CPU Space process per command | 18.0 ms | 13.4 ms |
| CPU Space process / command worker / web | 98 / 18 / 16 % | 91 / 36 / 19 % |

The read work has moved to the command worker (it keeps the copy ordered by type). The Space process still runs at a
good 90 % of a core, because it now lets more commands through: the world only uses more cores with several Spaces.

The rest of the work is spread widely (CPU profile with mirror, self time): garbage collection 6 %, measuring JSON size
for pages and the change stream 5 %, lease expiry per commit 5 %, claims on disk 4 %, store parts 4 %, searching and
comparing 10 %, the rest in small pieces. No single large item is left.

### Conclusions

- **One core carries about 70 commands per second** (local, with mirror), so about 150 figures at the pace of the test.
  More machines only help once the world consists of several Spaces ([welt-aufteilen.en.md](welt-aufteilen.en.md)); a third
  server (vpsc, 8 cores) brings nothing until then.
- **Splitting by island helps little here**: after 2 minutes, 198 of the 200 figures stood on the Graue Insel (8 rooms).
  A cut must follow the load (rooms of the starting island separated) or the start distributes the guests.
- **The page under load**: the own figure jumped back because the page gave up unanswered steps after 3 s
  (`RESYNC_MS` in `client/walk.ts`) and went to the last confirmed position; the late answers then brought it forward.
  Now it gives up only after 15 s (a lost intent expires after 30 s).
- **The starting bay** needs a keeper who keeps up, or a fire that does not go out completely without players.

## Four regions (local, 200 figures, 60 s, SQLite)

After splitting the world ([welt-aufteilen.en.md](welt-aufteilen.en.md)): per region one Space process, one world worker and
one NPC process, new guests start in turn in the four starting bays (`tests/perf/region-cost.ts`, development machine).
As with `space-cost.ts`, the NPC roles Ines, Bo and the Fremde play; with all 34 roles in every region the figure is
given beside it.

| | one Space, with mirror | four regions | four regions, all NPC roles |
|---|---|---|---|
| Commands per second | 67.9 | 69.1 | 79.3 |
| Response median / p95 | 75 / 353 ms | 31 / 161 ms | 41 / 861 ms |
| CPU Space process(es) | 91 % | West 64, Nord 54, Ost 76, Süd 46 % | 63 / 63 / 81 / 57 % |
| CPU world worker | 36 % | 11 / 11 / 13 / 8 % | 11 / 12 / 14 / 10 % |
| CPU web | 19 % | 21 % | 26 % |

At this pace the figures send no more than 70 to 80 commands per second (1 to 3 s pause after each answer); the
strongest Space is now at three quarters of a core instead of a whole one, the answers come twice as fast. **Together,
however, the four Spaces compute clearly more per command** than one (about 35 instead of 13 ms CPU): each region has
its own ticks (fire, fog, tide, appointments, clean-up), a crossing is three commits in two Spaces, and four Spaces
each wait for work on their own. What exactly causes it has not been measured yet; it is the next place to start, so
that the regions not only distribute but also save.
