# Load test 2026-11-13: 200 players who play everything, big and locally under a profiler

`tests/perf/play-load.ts` ([betrieb.en.md](betrieb.en.md), "Players who play everything"): 200 registered players, epoch 4
forced, activities of all four epochs at random with 1 to 3 s between two commands; model calls off while they played.
Each player's things come from the driver (into the pack through the region spaces), so the world fills faster than with
real players: a run of 30 minutes took the regions from 2,600–7,000 things to 15,000–40,000.

## big, 30 minutes (commit 59a52a1)

Backed up before (`mmo-backup` by hand, big and nano) and put back afterwards (the whole game stopped, the four world
Spaces, the NPC memory and nano's accounts Space written back, counts checked against the ones before). The run of 300
players was not started.

## Locally, the web process under a profiler

The local test bed (`docker:local:rust`) with its web container stopped and `mmo-web` built with line tables
(`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`) on this machine; `eu-stack -i` sampled it about once a second (no perf
here), 15 minutes, 200 players, the test bed's volumes put back before each run and after.

Before: busy in 94 % of the samples. 72 % in `atlas_state`: on every change of the overview it ran for every client and
went over every object of the world twice (`stops`, the same for every client, and `todos_for`), and it read three
settings from the space each time (600 calls per broadcast at 200 players). 9 % in `msg_view` → `for_viewer`: a Unicode
regex of the viewer's name compiled anew for every message and every viewer.

The fix: `atlas_shared` builds what every client's state shares once per broadcast (the owned things, the objects each
character has tasks of, people, fog, fires, epochs, stops) and reads the settings once; `named_in` keeps the compiled
name pattern per name. The frames are the same (`web-cross`: no differences).

| | before | after |
|---|---|---|
| `mmo-web` busy | 94 % | 28 % |
| Commands in 900 s | 19,792 | 29,739 |
| Median in the first 2 minutes | 5.0 s | 0.6 s |
| Unanswered after 10 s, whole run | 33 % | 11 % |

After the fix the answers still slowed down as the world filled (median 8 s after 15 minutes): the Space processes were
the limit then, and stayed busy after the players were gone.

## Locally, a Space process under a profiler

The region Space ost of the test bed, sampled with gdb every 2 s (the binary has symbols; `set sysroot /proc/<pid>/root`
reaches the container's libraries), 15 minutes each, 200 players, the fixed web process, the volumes put back before each
run. The changed `phi-space-server` was copied into the four region containers for the runs (the image build had no
network that night).

Busy 90 %, almost all of it in commits: 45 % settling the waiting operations after every commit, a lease renewal among
them (`Space::settle_batch` → `serve` → `find`), where `find` went over every record of the space for every waiter of a
rare type (an Intent among 20,000 things); 21 % in `SpaceHost::plan`, which went over every record and hashed its id to
find the few a commit touched.

The fixes, in phi-core and phi-store: `find` looks only at the records of the template's type (the type buckets `list`
already used, in the records' order: the same first match), and a removal moves the buckets' positions instead of
dropping them; `plan` works out the touched records' places from the commit's log (a push appends, a removal moves the
later ones up, a change names its place) and looks at every record only when that does not fit the records (a debug
build checks it against the full pass on every commit).

| | web fix only | + `find` by type | + `plan` from the log |
|---|---|---|---|
| Commands in 900 s | 27,462 | 33,013 | 38,853 |
| Space west / nord / ost / sued CPU avg | 93 / 90 / 93 / 73 % | 79 / 74 / 81 / 43 % | 60 / 58 / 68 / 40 % |
| Median, minutes 12–15 | 8.8 s | 3.7 s | 3.6 s |
| Unanswered after 10 s, minutes 12–15 | 45 % | 20 % | 18 % |

What is left in ost: `read_all` 29 % (the pages of `readAll`, a scan of a type's records against the template's fields),
commits 28 %, `Object::position` (a field looked up by name) 7 %. The answers still slow down over the run as the driver's
things pile up in the world; the world processes rose to 30–50 % CPU now that the spaces answer faster.
